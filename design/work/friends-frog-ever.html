Friends Frog-ever

Our team wrote its own C++ game engine. I built the level editor on top of it, modelled on Unity, so our two design students could build a 3D stealth game without writing engine code.

01 · The problem

Two designers, and an engine only programmers could use.

Friends Frog-ever (first called Ribbit Express) is a 3D stealth game: a little frog sneaks through a shipping yard, past patrolling robots, to fix its robot friend. We built it on our own C++ engine instead of Unity or Unreal.

That created a problem. Without an editor, every change to a level, like moving a crate, adjusting a light or wiring up a menu button, meant a programmer editing code and rebuilding. With two design students responsible for building the levels, the programmers would become the bottleneck for everything.

My thinking

My users weren’t players. They were my two teammates. They already knew how to build levels in Unity from class, so the fastest way to make them productive was to give them something that felt like Unity, not a new tool they’d have to learn mid-project.

02 · The editor

Everything a designer needs, in one window.

I built the whole editor: every panel, the tools inside them, and how they talk to the engine. Designers could build a scene, test it and fix it without leaving the window.

  • Scene viewport: play the scene in place, move, rotate and scale objects with gizmos, switch between world and local space, and jump between five camera views.
  • Hierarchy and inspector: every object in the scene as a tree, with parents and children. Select one to add or remove components and set its layer, just like Unity.
  • Resource panel and prefabs: browse models, textures, audio and scripts by folder, and reuse objects as prefabs.
  • Script editor: open and edit the game’s Lua scripts right next to the scene, or send them to VS Code.
  • Scene manager: create, load and save scenes such as the menu, settings, credits and cutscenes.
  • Debug panel: frame time, an undo and redo history for every edit, and a log console filtered by trace, info, warning and error.
  • Audio controls: a volume mixer for UI, music and sound effects, with 3D sound settings.

03 · Trade-offs

The calls I made, and what they cost.

Decision

What should the editor look and feel like?

  1. ✓

    Mirror Unity: same panels, same words (chosen)

    Hierarchy, inspector, components, prefabs. The designers already knew where everything was, so they could start building straight away. Costs: some Unity ideas didn’t map neatly onto our engine, so I had to bend the engine to fit.

  2. ✕

    Design our own layout around the engine (not chosen)

    Could fit the engine more naturally, but the designers would be learning a new tool while also building levels.

Decision

Where should designers edit scripts?

  1. ✓

    Inside the editor, next to the scene (chosen)

    Change an enemy’s behaviour and test it without switching windows. Costs: a second, simpler code editor to build and maintain, so I added a shortcut to VS Code for bigger edits.

  2. ✕

    Only in an external code editor (not chosen)

    Less for me to build, but constant switching between tools slows down the try, test, fix loop that level design depends on.

Decision

How safe should it be to experiment?

  1. ✓

    Undo and redo for every edit (chosen)

    Designers could try things without fear of breaking the level. Costs: every change had to go through one command system, which made each new tool more work to add.

  2. ✕

    Save often and hope (not chosen)

    Simpler to build, but one bad drag could cost a designer their afternoon.

04 · The game

What the designers built with it.

The levels, menus and cutscenes in Friends Frog-ever were put together in the editor. The game shipped on Windows and Android, with touch controls on mobile.

05 · What I learned

Building tools is designing for people.

Familiar beats clever. Copying a layout the designers already knew saved more time than any new idea would have.

Undo makes people brave. When mistakes are cheap, designers try more things, and the levels get better.

Sit with your users. The best requests came from watching the designers work, then turning what slowed them down into the next feature.
